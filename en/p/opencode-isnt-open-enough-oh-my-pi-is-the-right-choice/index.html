opencode isn't open enough; oh-my-pi is the right choice

A cache-read bug that sat at P3 for five weeks made me recalculate what "open" is actually worth — source-visible ≠ governance-responsive, and open code ≠ open decisions.

I’ve written a dozen posts recommending opencode. Today I’m retracting.

How I got here

Since January, opencode + Zhipu Coding Plan has been my daily driver. I wrote about how it saves money, how it dodges vendor lock-in, how to wire up MCP tools — you can dig a dozen such posts out of this repo:

  • High efficiency on a budget: my AI agent workflow — the opencode + Gemini money-saver combo
  • OpenCode config optimization notes — token and config tuning
  • MCP tools worth using — tooling recommendations
  • Automating GitHub PR code review with OpenCode + GLM-5 — CI automation
  • OpenCode plugin optimization — the plugin surface in depth
  • Three bugs in opencode’s LLM provider — early bug analysis

Three months ago, in From saving money to worry, I said “keep using it, but stay watchful.” Two months ago, in Switching from claude code to omp, I recommended opencode and omp side by side.

Four months in, I’ve fully changed my mind. Not because opencode got worse — because it showed me what the word “open” is actually worth.

Here’s the conclusion up front: opencode isn’t open enough; oh-my-pi (omp) is the right choice.

A bug

First, a true story: sun-praise/opencode-actions#278.

I was running opencode + litellm with DeepSeek for a multi-review dogfood run. Something odd: opencode always records tokens_cache_read as 0 — even when upstream DeepSeek returns cached_tokens, even when DeepSeek’s server is actually billing ~98% of the prompt as cache hits.

Sounds like a small bug, but the damage is real:

  1. The cost table is wrong. In the multi-agent review cost table posted to the PR, every persona’s Cache Read column reads 0, while DeepSeek is actually charging cache prices.
  2. It got misread as “resume costs more.” PR #277’s dogfood measured session-resume input tokens at 2.2× fresh (76k → 168k), making resume look more expensive. The truth is the repeated prefix mostly hit DeepSeek’s cache (~10% price), but opencode records that column as 0, manufacturing the illusion of a full-price doubling.

The contrast stings: in the same opencode install, zhipu/glm and minimax both record cache_read correctly. Only litellm/* is 0.

I did everything I could

I traced the bug — openai-chat.ts:mapUsage maps cached_tokens to cacheReadInputTokens, and publish-llm-event.ts reads that field, but the openai-compatible path drops the value somewhere between mapUsage and the session write.

I filed the upstream issue (anomalyco/opencode#34022) with full diagnosis, reproduction path, comparison data, and acceptance criteria. In my own repo I finished the triage, traced the data flow line by line, and explained “nothing can be fixed here — the SDK hands me 0, I can’t fabricate numbers.”

Then what

P3, needs-info, shelved.

From June 26 to today (July 30), five weeks. The “solution” I got was: switch providers.

Switch the dogfood model to a provider opencode already reads cache for correctly.

Those are my own words in the workaround. I didn’t feel the sting when I wrote them. In hindsight — a bug in an open-source tool, and the final answer is “just don’t use that provider.”

It’s not just a bug

My point here isn’t “opencode has bugs” — all software does. The point is this incident broke my understanding of “open” into three layers, and opencode is stuck on every one.

Layer one: source-visible ≠ you can fix the version you’re running.

opencode is open source. I can see every line of code; I even located the bug. But I can’t fix the opencode I’m actually running — unless I fork, maintain that fork, and rebase against upstream forever. That’s a lot closer to “commercial software has a bug, wait for the vendor” than I’d assumed. The “open-source safety net” is real, but it’s “when things break you can stay on an old version,” not “when things break you can make it better.”

Layer two: open code ≠ open governance.

I filed the issue, wrote the full diagnosis, gave acceptance criteria. Then it got dropped to P3, tagged needs-info, and sat for five weeks. Issue triage, priority, who fixes what first — those are core-team decisions, and the community can’t get in.

And it’s not just issues. When I scrolled through opencode’s GitHub back in From saving money to worry, I’d already seen it: stacks of PRs sitting for weeks or months, unmerged, unreviewed. People willing to contribute, but nobody with the bandwidth or the process to catch those contributions. That’s the other side of issue #278 — I got shelved as a bug reporter; those PR authors got shut out as contributors. Open source promises “you can participate,” but if your PR rots in the queue, that door is effectively closed.

For the bazaar model to work, there has to be “a seemingly loose but always-operating hand” merging and triaging. opencode’s hand has stalled. The foreshadowing I planted four months ago — “if still nobody’s handling it, I’ll start looking elsewhere” — has now come due.

Layer three: open code ≠ open decisions.

The “switch provider” workaround is, at its core, the maintainers’ priority telling me: litellm/deepseek compatibility isn’t worth the time. I can’t influence that priority. The name says open, but which providers matter, which features ship first, which bugs get fixed first — direction is set unilaterally by the core team. The code is laid out in front of you; the decisions are out of reach.

Why omp is the right choice

Three reasons, in order of importance.

One: it iterates fast — the most visible thing.

omp ships a commit almost every day. /goal, /loop, workflow — these new paradigms are still queuing in opencode’s issues, but omp has them all. For a fast-evolving category like coding agents, “capability-evolution speed” is itself part of being open — a project that stops evolving has an open-ness of zero, because nobody’s iterating anymore.

Two: it’s architecturally open.

I wrote about this separately (What components does oh-my-pi actually use?). omp is a fork + selective backport of pi-mono, not a closed-door build:

  • Three scopes (@oh-my-pi/*, @mariozechner/*, @earendil-works/*) all resolve to the same code — upstream pi plugins just work;
  • A complete SDK / Extension / Hook plugin surface, with 15 SDK examples from hello-world to Redis persistence;
  • CLI and SDK are the same package — no “SDK sold separately” split.

This is openness built into the architecture, not just “the code’s on GitHub.”

Three: the harness has to be in your own hands.

This is the core of my hot take from June: LLM vendors are racing to build their own harnesses — MiniMax, Kimi Code, CodeX, DeepSeek — vendor lock-in is what vendors want and what you should fear. As a user, the agent harness has to be in your own hands. With omp you can fork, backport, and build your own exclusive layers (it did exactly that: pi-natives, hashline, swarm-extension).

Redefining “open”

After these four months, I’ve redefined my requirements for “open”:

opencodeomp
Source visible✅✅
Governance responsive⚠️ backlog, P3 shelved✅ daily iteration
Capability evolving⚠️ slow feature delivery✅ fast new-paradigm uptake
Decision participation❌ core team unilateral✅ fork+backport is self-determination

open = source-visible + governance-responsive + capability-evolving + decision-participatory.

opencode has the first box. omp has all four.

Closing

When I wrote From saving money to worry, my conclusion was “keep using it, but stay watchful.” Back then I was still willing to wait. Three months on, that “merging hand” hasn’t come back.

So I’ve stopped waiting. The old-version safety net is still there — when I can’t use opencode’s latest, the old version genuinely still runs. But “still runs” isn’t what I want. I want “still getting better, and within my reach.”

This isn’t opencode’s failure. It’s that my bar for the word “open” has gotten higher.

opencode isn’t open enough; oh-my-pi is the right choice.
