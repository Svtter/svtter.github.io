pi-review-agent 跑 AACR-Bench

把 pi-review-agent 接上阿里的 AACR-Bench：166 个真实 PR、三档 diff 预算、66M token，最终语义 F1 8.1%——评审能力不算强，但成本够低；外加截断、超时、缓存三个意料之外的发现。

pi-review-agent 是我维护的多 persona AI code review agent，上一篇讲过它怎么跨 run 续接会话。 我自己的几个项目——包括 pi-review-agent 和 pi-review-dashboard——日常代码评审都跑在它上面。

最近注意到阿里的 AACR-Bench：166 个真实 GitHub PR、1231 条专家验证的评审标注。正好拿它测一测 pi-review-agent 的评审水平，也给后续怎么安排 review 工作一个量化依据。

这篇文章记录实验全程：怎么接入、分数多少、三个跑完才发现的意外。先说结论：语义 F1 8.1%，和 Codex + GPT-5.5 同档，距离 Open Code Review + Deepseek-V4-Pro 的 17.9% 还有 10 个百分点。分数不算亮眼，但它便宜——模型用的是便宜一档的 mimo-v2.5。

便宜模型跑 review 是不是好买卖，我到现在也没完全想清楚，但至少账算得明白。而且实验本身比分数有用：好几个“差距来自哪里”的假设，跑完都被证伪了。

接入：一次 PR 加一个 reviewer 模块

pi-review-agent 原本强依赖 GitHub/Gitea 环境，PR 评论就是它的输出面；基准 harness 要的却是 无头模式：给一个 commit 对，吐出结构化 findings。改动有两处：

  • 给 agent 加了 --format json 免平台模式（PR #70）： 不再要求 --pr、不建平台适配器、不发评论，stdout 输出单个 JSON，包含验证过的 findings、 逐 persona 用量和 verdict/severity。--session-key 顶替 PR 号做会话隔离，消毒后落盘， 防止 benchmark 多实例互相串会话。
  • 照着 harness 里 codex reviewer 的模板写了 reviewers/pi.py：克隆仓库、checkout 到 head、 git diff base head 喂进去，把 payload 包成标准结果文件。

接入时顺手做了反作弊审计：评审器收到的输入只有 diff 和仓库工作区，参考标注从不进入任何输入； 工具面只有 read 和 grep，没有 shell 和网络。跑完又对生成意见和参考标注算了 3-gram 重叠： 最高 0.31、中位数 0，是“各自表述同一个问题”的形态，不是背题。

成绩单

166/196 个实例进了评测。30 个实例的 PR 被 rebase 过，head commit 在 GitHub 上已不可达，剔出分母； 官方基线同样受此约束。语义匹配的判定链：文件相同 → diff 侧相同 → 行号 ±1 → judge 模型 判定语义一致。

pi-review-agent（终版）mimo-v2.510.2%6.7%8.1%
OCRDeepseek-V4-Pro30.6%12.7%17.9%

（官方数字来自 OCR 仓库排行榜，各家的数据集、模型与 judge 不完全一致，只供量级参照。）

两个读数。一是 P/R 均衡（10/6.7），不像 Claude Code 靠刷召回（7/29），也不像 Codex 偏科精确（28/5）。 二是行号 F1（12.5%）高于语义 F1：模型经常站对了行，但对“这行有什么问题”的判断和专家不一致。 OCR 用规则引擎硬编码高频缺陷模式，多半就是不信任模型的这部分直觉。

表里看不出来的还有成本。mimo-v2.5 对位的是别家旗舰，本身便宜不少；多 persona 重复的 diff 输入又被前缀缓存基本吃掉，295 次实例评审的总账单只有 66M token，88% 按 cacheRead 计价（细账见意外三）。 所以对这套组合的诚实评价是：评审能力确实不算强，但它花的钱也少。卖的是性价比，不是绝对分数。

意外一：截断不是主因

pi-review-agent 默认 --diff-max-size-kb 200。考古了一下，这个值当初是为了防 LiteLLM 代理的 HTTP 413（6MB 的 dist bundle 曾经直接打挂全部 reviewer），不是按模型上下文算的。基准里 47.6% 的实例（79/166）被这个默认值截断，我一开始把低分主要归咎于此，于是放开预算重跑这 79 个：

预算档实例有效率findings结果
200KB166100%79679 个被截断，基准 F1 7.6%
1MB7937%147大面积超时（见意外二）
400KB50100%276全部有效
合并终版166100%802F1 8.1%，只涨了 0.5 个点

1231 条参考标注里，放开截断只多命中 5 条。模型看到了完整代码，依然没把问题挑出来。 瓶颈在检出能力，不在输入完整性。直觉会高估“给模型更多上下文”的收益——这是这次实验最贵的一课， 学费约 4000 万 token。相关讨论记在 issue #71。

意外二：1MB 输在时间，不在容量

1MB 批 63% 的实例三个 persona 全军覆没，错误是 Request timed out.。第一反应是代理扛不住。 直接拿 28.6 万 token 的请求打代理实测：预填充 32 秒完成，没有 413 也没有掐断，链路容量根本不是问题。

真凶是超时栈里藏着的两层。--timeout-seconds 1800 只是外层评审超时；provider 里的 OpenAI SDK 还有一个默认 600 秒的内层请求超时，不可配置，也不随外层传播。mimo 是推理模型，30 万 token 的上下文上要先生成长推理链再写评审，单请求轻松超过 10 分钟，内层先爆，重试再爆。400KB 档 输入砍半，生成时间落回安全区，100% 存活。所谓“400KB 甜点”就是这么来的：它不愁容量，愁的是时间。 修复方向（超时传播 + 报错区分两层）记在 issue #72。

意外三：88% 的 token 走了缓存价

全项目总账，295 次实例评审：

批次实例findings非缓存输入输出cacheRead小计
全量首轮（200KB）1667961.2M1.0M24.1M26.3M
补跑 1MB791473.7M0.2M16.4M20.3M
补跑 400KB502760.2M0.3M18.9M19.5M
合计29512195.2M1.5M59.4M66.1M（缓存占 88%）

66M token 里 88% 是 cacheRead。三个 persona 共享同一份 diff，DeepSeek 式前缀缓存让第二、 第三个 persona 的 diff 部分几乎全价打折。换句话说，多 persona 架构最被诟病的“重复输入”， 在正确的计费口径下基本免费。pi-review-agent 的 cacheRead 记账（当初是为了修 opencode 的 tokens_cache_read 恒零 bug 做的设计）也因此第一次在外部基准上拿到实据。 OCR 的榜单只报 token 相对量，没有这层账。

局限

  • judge 同源：语义裁判是 mimo-v2.5-pro，判 mimo-v2.5 的输出，松紧未知；行号指标不受此影响。
  • 模型归因：分数上看，mimo-v2.5 和榜上别家旗舰差 10 个点，但模型和架构各贡献多少还没分离。 干净的归因要用 OCR + mimo 同模型同代理跑同样本，这是下一步。
  • 出题人问题：AACR-Bench 和 OCR 同出阿里，标注口径天然贴近 OCR 规则引擎的输出形态。 它是合格的工程基准（开源、专家交叉验证、强基线同 harness），但“绝对名次”要打折读。
  • 30 个不可达实例带着全数据集约四成参考标注，评测子集偏小。

下一步

  1. OCR + mimo-v2.5 同条件对照，把“架构值多少分”归因干净；
  2. 修 #72（超时传播），用真实的长超时 重测 1MB 档，补全“预算-超时-覆盖”这个三角；
  3. 更远的事：超大 diff 的文件捆绑分治。OCR 用代码做 bundle、agent 只管推理，这套思路 和 pi 的 related-context import 图可以拼起来。

数据都在本地：aacr-bench/evaluation/results/（逐实例结果 JSON）、evaluation/PI_AACR_RESULTS.md（汇总表）、 reviewers/pi.py（评审器接入，在 aacr-bench 的 pi-reviewer 分支）。基准本身在 alibaba/aacr-bench，模型是自建 LiteLLM 代理上的 mimo-v2.5。 有想法欢迎去 pi-review-agent 的 issue 区聊。
