opencode 不够 open；oh-my-pi 才是正确的选择

一个被压成 P3 晾了五周的 cache-read bug，让我重新理解了"open"这个字到底值多少——源码可见不等于治理响应，开源代码不等于开源决策。

我写过十几篇推荐 opencode 的文章。今天改口。

缘起

从 1 月起，opencode + 智谱 Coding Plan 是我的主力。我写过它怎么省钱、怎么避开厂商锁定、怎么搭 MCP 工具——这仓库里能翻出十几篇：

  • 《高效省钱：我的 AI Agent 工作流选择》— opencode + Gemini 的省钱组合
  • 《OpenCode 配置优化记录》— Token 和配置调优
  • 《最近发现好用的 MCP 工具》— 配套工具推荐
  • 《使用 OpenCode + GLM-5 实现 GitHub PR 自动代码审查》— CI 自动化
  • 《opencode 插件优化》— 插件体系深度
  • 《opencode LLM provider 的三个 bug》— 早期 bug 分析

三个月前我还在《从省钱到担忧》里写"继续用，但保持关注"。两个月前在《从 claude code 转向 omp》里，我把 opencode 和 omp 并列推荐。

四个月用下来，我彻底改主意了。不是 opencode 变差了，是它让我看清了"open"这个字到底值多少。

结论先放这：opencode 不够 open；oh-my-pi (omp) 才是正确的选择。

一个 bug

先讲一个真实的故事，sun-praise/opencode-actions#278。

我用 opencode + litellm 跑 DeepSeek 做 multi-review dogfood。发现一个怪事：opencode 永远把 tokens_cache_read 记成 0——即使上游 DeepSeek 返回了 cached_tokens，即使 DeepSeek 服务端实际上把约 98% 的 prompt 命中了缓存。

听起来像个小 bug，但它的杀伤力是实打实的：

  1. 成本表是错的。 多 agent review 贴到 PR 的成本表里，每个 persona 的 Cache Read 列都是 0，而 DeepSeek 实际在按缓存价计费。
  2. 它让人误读成"resume 更贵"。 PR #277 的 dogfood 测出 session-resume 的 input token 是 fresh 的 2.2 倍（76k → 168k），看上去 resume 反而更烧钱。真相是重复前缀大部分命中了 DeepSeek 缓存（约 10% 价格），但 opencode 把这一列记成 0，造出了"全价翻倍"的错觉。

对比很扎眼：同一个 opencode 安装里，zhipu/glm 和 minimax 都能正确记录 cache_read，只有 litellm/ 是 0*。

我做了能做的一切

我查到了 bug 的位置——openai-chat.ts:mapUsage 把 cached_tokens 映射到 cacheReadInputTokens，publish-llm-event.ts 读这个字段，但 openai-compatible 路径在 mapUsage 到 session 写入之间把值弄丢了。

我提了 upstream issue（anomalyco/opencode#34022），附上完整诊断、复现路径、对比数据、验收标准。在自己的 repo 里把 triage 写完，把数据流逐行点清，说明"这个 repo 里改不动——SDK 给我就是 0，我不能凭空造数字"。

然后呢

P3，needs-info，晾着。

从 6 月 26 日到今天（7 月 30 日），五个星期。我得到的"解决方案"是：换 provider。

Switch the dogfood model to a provider opencode already reads cache for correctly.

这是我自己写在 workaround 里的话。我写的时候没觉得扎心，现在回味过来——一个开源工具的 bug，最终答案是"你别用这个 provider"。

这不只是一个 bug

我用这个故事想说的，不是"opencode 有 bug"——软件都有 bug。我想说的是，这件事把我对"open"的理解拆成了三层，每一层 opencode 都卡住了。

第一层：源码可见，不等于你能改掉你正在跑的那个版本。

opencode 是开源的。我看得见每一行代码，我甚至定位到了 bug 在哪。但我不能改掉我正在用的那个 opencode——除非我自己 fork、维护一个 fork、跟着上游 rebase。这跟"商业软件出了 bug 只能等官方"的区别，远比我以为的小。那个"开源安全垫"是真的，但它是"出事了你可以停在旧版本"，不是"出事了你可以让它变好"。

第二层：开源的代码，不等于开源的治理。

我提了 issue，写了完整诊断，给了验收标准。然后它被压成 P3，挂上 needs-info，晾五个星期。issue 分类、优先级、谁先修——这些都是核心团队的决策，社区进不去。

而且不止是 issue。我在《从省钱到担忧》里翻 opencode 的 GitHub 时就看到过：大量 PR 堆了几周甚至几个月，没人合并、没人 review。有人愿意贡献，但没人有精力、有流程去接住这些贡献。这就是 issue #278 的另一面——我是 bug 报告者被晾着，那批 PR 的作者是贡献者被拒之门外。开源承诺的是"你可以参与"，但如果 PR 在那儿烂掉，这扇门其实就是关着的。

集市模式要运转，前提是有一只"看似松散但始终在运作的手"在合并、在 triage。opencode 这只手停摆了。四个月前我埋的伏笔——“如果还是没人管，就开始看别的方案”——现在兑现了。

第三层：开源的代码，不等于开源的决策。

“换 provider” 这个 workaround，本质是维护者的优先级在告诉我：litellm/deepseek 的兼容性不值得花时间。我没法影响这个优先级。名字叫 open，但哪些 provider 重要、哪些功能先做、哪些 bug 先修——方向由核心团队单方面拍板。代码在你面前摊开，决策却在你够不到的地方。

为什么 omp 才是正确选择

三个理由，按重要性排。

一、迭代快，这是最直观的。

omp 几乎每天一个 commit。/goal、/loop、workflow 这些新范式，opencode 还在 issue 里排队，omp 已经全跟上了。对 coding agent 这种高速演化的工具，“能力进化速度"本身就是 open 的一部分——一个不再快速进化的开源项目，open 度是归零的，因为没人在迭代了。

二、架构层面真 open。

这个我单独写过（《oh-my-pi 用到了哪些基础组件》）。omp 是 pi-mono 的 fork + selective backport，不是闭门自造：

  • 三个 scope（@oh-my-pi/*、@mariozechner/*、@earendil-works/*）写哪个都解析到同一份代码——上游 pi 的插件可以直接用；
  • 完整的 SDK / Extension / Hook 插件体系，15 个 SDK 示例从入门到 Redis 持久化；
  • CLI 和 SDK 是同一个包，没有"SDK 单独卖"的割裂。

这是把"开放"做进了架构，不是停在"代码挂在 GitHub 上”。

三、harness 必须攥在自己手里。

这是我 6 月那篇暴论的核心：大模型厂商纷纷自建 harness——MiniMax、Kimi Code、CodeX、DeepSeek——vendor-lock 是厂商追求的，是你该警惕的。作为用户，agent harness 一定要掌握在自己手里。omp 你可以 fork、可以 backport、可以自建独占层（它自己就这么干的：pi-natives、hashline、swarm-extension）。

重新定义 open

走完这四个月，我重新定义了一下对"open"的要求：

opencodeomp
源码可见✅✅
治理响应⚠️ 积压、P3 晾着✅ 每日迭代
能力进化⚠️ 新功能落地慢✅ 快速跟进新范式
决策参与❌ 核心团队单方面✅ fork+backport 可自决

open = 源码可见 + 治理响应 + 能力进化 + 决策参与。

opencode 拿下了第一格，omp 四格全占。

收尾

我写《从省钱到担忧》的时候，结论是"继续用，但保持关注"。那时候我还愿意等。三个月过去，那只"合并的手"没有回来。

所以我不再等了。历史版本的安全垫还在——我没法用 opencode 最新版时，旧版本确实还能跑。但"还能跑"不是我要的，我要的是"还在变好，而且我够得着"。

这不是 opencode 的失败。是我对"open"这个字的要求，变高了。

opencode 不够 open；oh-my-pi 才是正确的选择。
