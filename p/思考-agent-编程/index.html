思考 agent 编程

读完亚马逊团队的博客 How frontier teams are reinventing AI-native development，我对 agent 编程有了新的认识：AGENTS.md、skills 与流程是新的代码，harness 是新的编译器。本文整理了关于这一新产业/供应链的思考。

AGENTS.md、skills 与流程，是新的代码；harness 是新的编译器。

最近读了亚马逊团队的博客 How frontier teams are reinventing AI-native development，产生了一些新的想法。

新的代码：AGENTS.md / skills / 流程

现在工程师编程，很多是围绕 AGENTS.md 来做的。也就是说，工程师下一步的工作，是如何构建好项目的 AGENTS.md、skills 以及流程。

这些东西是新的代码。harness 实际上是新的编译器：它把 AGENTS.md 等一系列内容作为输入，生成工作流来工作。就像编译器把源代码编译成机器指令，harness 把项目规范编译成 agent 可执行的工作流。

这是一个新的产业/供应链

由此衍生出一个新的产业和供应链：

  • 上游是模型厂商，提供 LLM 本身；
  • 中游是 harness 厂商，负责把项目规范编译成工作流；
  • 下游是工程师，负责编写和维护 AGENTS.md、skills 这些"新的代码"。

每一个环节都有独立的商业价值和竞争格局。

frontier 工程师需要理解 LLM 与 harness

对于一个 frontier 工程师，了解 LLM 和不同的 harness 很重要。

从性价比的角度来说，新的开源 harness，例如 opencode 或者 pi-agent，就是新的共享技术标准。每个新兴的大厂都试图控制这个标准——标准的争夺本身就是产业地位的争夺。

反过来，闭源的 harness、无法控制的 harness，很容易被放弃。

传统工程师：从写代码到专家

传统工程师，尤其是 senior 级别的，仍然可以解决一些 agent 无法解决的问题，但他们的身份更像是专家（oracle）了——不再是流水线上的写码工人，而是被调用的、回答疑难问题的权威。

结论

除了模型性能之外，harness 会很大程度影响工作流和团队的适配程度。选择 harness，和当年选择编程语言、选择框架一样，是一个影响长期生产力的决定。
