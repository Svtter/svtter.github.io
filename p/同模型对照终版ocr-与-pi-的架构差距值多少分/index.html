同模型对照终版:OCR 与 pi 的架构差距值多少分

OCR 和 pi-review-agent 用同一个模型、同一个裁判、同一批 152 个实例对跑: 语义 F1 21.4% vs 8.4%——架构差距 2.5 倍,而单位成本反过来 pi 便宜 2.9 倍。

语速

第一篇跑完 AACR-Bench 后留了个尾巴: pi-review-agent 8.1% 对 OCR 官方配 Deepseek-V4-Pro 的 17.9%,差距里混着模型档位和评测口径, “架构本身值多少分"没法归因。这一篇补上最后一块拼图:把 OCR 拉到和 pi 完全相同的条件下 对跑——同一个模型(mimo-v2.5,同一个 LiteLLM 代理)、同一个语义裁判(mimo-v2.5-pro)、 同一批实例(两家都有结果的 152 个,1167 条参考标注)。

生成量打平是这张表最重要的控制变量:两家说的话一样多(748 对 751), 差距全部落在"命中质量"上。同模型、同裁判、同题、同话量—— 2.5 倍就是两个架构的纯粹差距。

三个值得单独说的发现

1. OCR 的架构对模型档位近乎免疫——这才是它最狠的地方。 OCR 配我们这个便宜模型拿到 21.4%,比它官方榜上配 Deepseek-V4-Pro 的 17.9% 还高 (跨子集仅供参考,但量级说明问题)。规则引擎把高频缺陷模式硬编码、定位交给字符串匹配、 LLM 只做剩下的语义推理——模型越便宜,这套确定性工程的杠杆越大。反过来, pi 这种 prompt 驱动的架构才吃模型:差距在弱模型上被放大。

2. pi 的差距在"挑什么”,不在"站哪"。 pi 的行号 F1(12.6%)到语义 F1(8.4%)只掉 4 个点,保持率不低;绝对量级上它经常 站在正确的行前面,但对"这行到底有什么问题"的判断和专家不一致。这正好定位了 pi 缺的那层:高频缺陷模式的确定性规则——也是 OCR 最值得抄的部分 (拆过它的捆绑源码,设计本质是"LLM 提议、代码裁决")。

3. 单位成本反过来,这是质量-成本曲线上的两个点,不是输赢。 每条有效命中,pi 便宜 2.9 倍、快 1.5 倍;OCR 准 2.5 倍。OCR 全程烧了 366M token (pi 45M),两家 9 成 token 都走前缀缓存价——缓存经济学在两种架构上都成立, pi 的多 persona 重复输入在正确记账下接近免费,OCR 的深度仓库探索也被缓存兜住。

顺带修正一个我之前的说法

上一篇我曾断言 OCR “每次评审都是初次见面”——这不对,该文后来已直接修订(此处引用修正后的结论)。 OCR 的 action 提供三个跨 push 的连续性机制(默认关闭): checkpoint_range 只审上次覆盖之后的新提交、incremental 按行范围去重不重贴旧意见、 sticky_summary 原地更新摘要。真实的差异是深度:这些机制停在范围级 (审到哪了、贴过什么),pi 的会话记忆是会话级(作者对上轮意见改了什么、 哪些 issue 还开着)。“有没有"错,“多深"对。

收口

这个系列到这里闭环:pi 的 8.4% 不是模型不够好,也不(主要)是输入不完整, 是缺一层确定性工程。好消息是方向从未如此具体——规则层可以从 OCR 的公开设计反推, bundling 的源码已经拆过,related-context.ts 的 import 图就是现成的分组器。 在补上这层之前,pi 的叙事是"质量-成本曲线上的低成本点”:每条有效意见便宜 3 倍、 快一半,会话级记忆和成本可观测是基准考不出的差异。
